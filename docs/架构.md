# 架构

## 一、分层

```
┌──────────────────────────────────────────────────────────────┐
│ MainForm.cs（WinForms，单窗体）                                │
│  搜索 / 目录列表 / 章节勾选 / 进度与 ETA / 设置 / 番茄核心按钮   │
│  所有耗时操作都丢到后台线程，UI 通过 UiInvoke 回调              │
└───────────────┬──────────────────────────────────────────────┘
                │ ISite（站点抽象）
┌───────────────▼──────────────────────────────────────────────┐
│ Sites/                                                        │
│  BiqugaMobileSite  m.biquga.com：dindex 目录页并发 + 正文预抓   │
│  BiqugaSite        www.biquga.com：搜索、prev 反向遍历、base64  │
│  FanqieSite        fanqienovel.com：目录 JSON、风控识别         │
│  TomatoCore        第三方番茄工具的本地 HTTP API 客户端          │
└───────────────┬──────────────────────────────────────────────┘
                │
┌───────────────▼──────────────────────────────────────────────┐
│ Common/                                                       │
│  Http             取数：curl 子进程后端 → .NET 回退、重试、编码  │
│  DownloadRunner   流程：取正文 → 清洗 → 每 20 章 append → 收尾  │
│  TextCleaner      正文清洗（广告 / 分页残留 / 导航残渣）         │
│  DirCache         目录缓存（list.json + 可选正文缓存）           │
│  AppSettings      settings.ini：并发 / 间隔 / 重试              │
│  FontMap          可选 font-map.json：私用区字符还原             │
└──────────────────────────────────────────────────────────────┘
```

关键点：**界面、命令行自测（`_selftest.exe`）、批量工具（`_dl.exe`）走的是同一套
`DownloadRunner`**。所以「测试跑通」等于「界面里能用」，不会出现两套逻辑各错各的。

## 二、一次完整下载的数据流

```
用户输入书名
   │
   ├─ BiqugaSite.Search         POST /search.html（字段 s）→ 解析结果表
   │
   ├─ LoadBook（两条路）
   │    ├─ 移动版：m.biquga.com/{dir}/dindex_1..N.html  ← 8 线程并发，11 页 / 1067 章 / 1.48 秒
   │    │          每页 100 章，解析出 cid + 标题 + 分卷
   │    └─ PC 版：从最后一章沿 var uiiekp0do（上一页）反向走到目录页
   │              （next 链接不可靠，会成环；prev 完全可靠）
   │
   ├─ 离线模式：并发把每章正文预抓进内存（BiqugaMobileSite.PrefetchText）
   │
   └─ DownloadRunner.Run
        for 每章：
          ├─ c.Text 或 ITextCacheProvider.GetCachedText(cid)  ← 目录阶段已抓的正文
          ├─ 否则 Site.LoadChapter()       ← base64 解 document.writeln(qsbs.bb('…'))
          ├─ 正文 < 40 字 → 计入 Skipped（站点侧空内容）
          ├─ 异常 → 计入 Failed，记原因
          ├─ TextCleaner.CleanBody()        ← 切行尾广告、去分页残留、丢弃广告行
          └─ 每 20 章 FlushIncremental()     ← append 写盘（不是重写整个文件）
        收尾：
          ├─ RetryPasses 轮重试（只重失败的那几章）
          ├─ FixHeaderNow()                 ← 在预留的 2KB 表头区内原位更新统计
          └─ WriteMissingReport()           ← 生成 .缺失章节.txt（有缺章时）
```

### 输出文件的字节布局

```
[EF BB BF]                         UTF-8 BOM，记事本/手机阅读器直接识别
[表头   ~400 字节]                  书名/作者/来源/简介/统计/时间 + 46 个等号
[\n 补白 至 2048 字节]              预留区：收尾改统计时原地写，正文位置永不变
[#header-zone:2048\n]              预留区标记：老文件没有它 → 只降级不改写
[正文 …… append 追加 ……]           每章：\n\n标题\n----\n\n正文\n
```

## 三、为什么是这几个设计决定

| 决定 | 原因 |
| --- | --- |
| 用 `curl.exe` 子进程取数 | biquga 只提供 TLS 1.3 且拒绝 .NET 的握手（`Received an unexpected EOF`），而系统自带 curl 正常。curl 不可用时自动回退 .NET 原生请求 |
| 不用 `HttpClient` / 异步 | .NET Framework 4.8 上 `HttpClient` 同样过不了那道 TLS；且 WinForms + `async` 在这个体量下不划算，用后台线程 + `UiInvoke` 更直白 |
| 增量 append 而不是攒完一次写 | 1000+ 章、10+ MB 的文件在收尾阶段重写会拖十几分钟；append 让中断也有半个文件 |
| 收尾原位改表头 | 表头要写准确统计（成功/跳过/失败），但整文件重写太贵 → 预留 2KB 定点改写 |
| 缓存目录到 json | 遍历目录是**串行**过程（PC 版 2 小时），必须能复用；缓存超 72 小时才算过期 |
| 站点差异放 `ISite`，公共逻辑放 `Common` | 移动版和 PC 版的目录结构完全不同，但清洗/落盘/报告完全一样 |
| 零第三方依赖 | 用户要的是「免安装单文件 exe」；引一个包就要跟着带一堆 dll |

## 四、并发模型

| 场景 | 线程数 | 位置 |
| --- | --- | --- |
| 移动版目录页 | `BiqugaMobileSite.Workers`（默认 8 / 在线 6） | 每页一个任务，`Parallel` 风格手工线程池 |
| 移动版正文预抓 | 同上 | 目录拿到后一次性并发抓全本 |
| PC 版目录遍历 | `BiqugaSite.CrawlWorkers`（默认 6） | prev 链本身串行，这个值主要限制正文并发 |
| 请求节流 | `Http.MinDelayMs~MaxDelayMs`（默认 60~180ms 随机） | 每章结束 `Http.Polite()`，随机间隔避免固定节奏 |

所有数值都能在界面的「设置」里改，落到 `settings.ini`，重启后生效。

## 五、测试策略

| 目标 | 内容 | 联网 |
| --- | --- | --- |
| `_offlinetests.exe` | 161 项：文件名清洗、HTML 工具、正文清洗（含历史 bug 回归）、缓存键、表头往返、缺失报告、FontMap | ❌ 不联网，CI 每次都跑 |
| `_edgetest.exe` | 边界 + 离屏真下载（真的起一个不可见的 `MainForm` 跑 `DownloadCore`） | ✅ 需要网络 |
| `_selftest.exe` | 分站点冒烟：`dl`（移动版小样本）、`biquga`、`fanqie`、`write` | ✅ 需要网络 |

**规矩**：任何被离线单测发现的产品 bug，修完必须补一条回归断言（例如
「带『推荐票』的长句不能被误判成广告」就是踩过坑之后加的）。
