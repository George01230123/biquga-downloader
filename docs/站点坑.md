# 两个站点的坑（实测记录）

这份文档里的每条结论都是**真机跑出来的**，不是推测。站点随时会改，
如果你按这里的做法失效了，八成是对方改了结构——先看本文的「怎么自己复现」，再提 issue。

---

## 一、笔趣阁（biquga.com）

### 1.1 TLS：只支持 TLS 1.3，而且拒绝 .NET 的握手

| 客户端 | 结果 |
| --- | --- |
| .NET Framework 4.8（`HttpWebRequest` / `SslStream`） | ❌ `基础连接已经关闭：发送时发生错误` → 内层 `Received an unexpected EOF` |
| .NET 10（`HttpClient`） | ❌ `SSL connection could not be established` |
| 系统 `curl.exe` | ✅ HTTP 200，约 0.8 秒 |
| Node.js | ✅ 正常 |

所以取数后端的**首选**是 Windows 自带的 `C:\Windows\System32\curl.exe`
（Win10 1803+ 系统内置，符合「免安装、零依赖」的目标），
找不到时自动回退 .NET 原生请求（番茄等站点原生可用）。

复现：

```powershell
curl.exe -s -o NUL -w "%{http_code} %{time_total}s`n" https://www.biquga.com/list/0/2.html
```

### 1.2 PC 版目录页是坏的

`www.biquga.com/{bid}_{aid}/index_N.html`（以及 `dindex_N.html`）会**串到别的书**：
例如 `/10_10333/index_1.html` 返回的是《倾尽天下》。**完全不能用。**

### 1.3 “下一章”链接不可靠（会成环漏章）

每章页面里有个 `var kkehvov`（下一章）。同一页多次请求会给出**不同结果**：
实测 `10032109` 的第 3 页，next 有时指第 4 页、有时指第 1 页。
顺着 next 走整本会成环 —— 实测 1600 页只凑出 **495 / 772 章**。

### 1.4 正解：改用“上一页”反向遍历（PC 版）

每章页面里的 `var uiiekp0do`（上一页）**完全可靠**：从最后一章一路 prev 走回目录页，
恰好覆盖 772 个页面（含章内分页），一章不漏。章节 id 单调递增，按 id 升序排就是阅读顺序。

代价是**串行**：一本 1000 章的书 3000~4000 次请求 × 每次 TLS 握手 0.9 秒 ≈ **2 小时**。

### 1.5 正文编码方式

正文是 base64 塞在 `document.writeln(qsbs.bb('...'))` 里，直接解码即可。
章内还有分页：`cid.html → cid_1.html → cid_2.html`。

### 1.6 移动版是完好的，而且快 10 倍以上（**默认推荐**）

`m.biquga.com/{书籍目录}/dindex_N.html` 每页 100 章，**结构完整**：

| 环节 | PC 版 | 移动版 |
| --- | --- | --- |
| 拿目录 | 顺链串行 700+ 次请求 | **11 次并发请求拿全 1067 章（实测 1.48 秒）** |
| 拿正文 | 每章 3~5 页串行 | 每章 1~2 页，8 线程并发 |
| 一本 1000 章 | 约 2 小时 | **约 10 分钟** |

**移动版的两个差异**：

1. 每章结尾会被站点**拼接一段广告**，而且是拼在正文句子后面的：
   `……他心中纳闷。还在为找不到的最新章节苦恼？安利一个公众号：rd444`
   → 必须按标记**切行尾**，不能整行丢弃，否则会连正文一起丢。
2. 每章页数比 PC 版少，正文内容一致。

**可靠做法**：用移动版目录页拿章节 id/标题（权威），用 PC 版搜索
（`POST /search.html`，字段名 `s`）找 `{bid}_{aid}` 目录。两者配合最稳。

## 二、番茄小说（fanqienovel.com）

### 2.1 没有可用的中文搜索接口

实测：

- `/api/search`、`/api/search?q=`、`/api/search/search_book/v1` → 404
- 从前端 JS 里挖出的真实接口 `/api/author/search/search_book/v1?query_word=中文`
  → HTTP 200 但**空 body**（需要签名/特殊上下文）
- 搜索页 `/search/<中文>` 能打开，但结果是 JS 异步加载：HTML 里是
  `searchBookList:null, loading:true`
- 伪装爬虫 UA（Googlebot / Baiduspider / Bytespider…）→ 只把 `isSpider` 置 true，仍不返回结果
- 用榜单接口建本地索引：有硬上限（`recent/update` 只有 100 本，`recommend` 只有 9 本，翻页无效），
  覆盖不了番茄的百万级书库

所以工具做的是「**浏览器搜索 + 粘贴链接**」的半自动流程：
点「浏览器搜索」打开官网搜索页 → 复制书籍链接 → 粘回输入框。
`FanqieSite.ExtractBookId` 认得下面这些形式：

| 粘贴内容 | 识别 |
| --- | --- |
| `https://fanqienovel.com/page/7406592861791063064` | ✅ |
| `7406592861791063064` | ✅ |
| `https://fanqienovel.com/page/7406592861791063064?enter_from=search` | ✅ |
| `https://fanqienovel.com/reader/7406592932351836696`（章节链接） | ✅ 会联网反查出书籍 id |
| `沧元图`（纯中文） | ❌ 会弹窗引导用「浏览器搜索」 |

### 2.2 目录接口是干净的

`GET https://fanqienovel.com/api/reader/directory/detail?bookId=<id>`
直接返回 JSON（书名、卷名、全部章节 id/标题）。实测《诡舍》一次拿到 1034 章 / 2 卷。

### 2.3 正文页有风控

连续请求后 reader 页会返回**验证码中间页**，甚至只给 **200 字试读**。
工具会识别这两种情况并**明确报错 + 跳过该章**，不会把残缺内容当完整章节保存。

### 2.4 网页正文还有“形近字替换”保护

常见字被换成形近字：`在→茌`、`特→恃`、`只→黒`、`出→岀`。
这是站点故意的可读替换，**离线无法完全还原**。

> 结论：**番茄正文不要用网页抓**。要么用官方 App/网页正常阅读，
> 要么用第三方番茄下载器（本工具支持对接它的本地 API，见 README 第三节）。

## 三、怎么自己复现这些结论

```powershell
# 1) TLS 差异：.NET 会失败，curl 正常
curl.exe -s -o NUL -w "%{http_code}`n" https://www.biquga.com/list/0/2.html

# 2) 移动版目录页：一页 100 章
curl.exe -s "https://m.biquga.com/69_69707/dindex_1.html" | Select-String "dindex|chapter" | Select-Object -First 5

# 3) 同一页的 next 链接不稳定（多跑几次看 var kkehvov 是否变化）
1..5 | ForEach-Object { (curl.exe -s "https://www.biquga.com/69_69707/10032109.html" | Select-String "kkehvov").Line }

# 4) 番茄目录接口
curl.exe -s "https://fanqienovel.com/api/reader/directory/detail?bookId=7256784068786785336" | Select-Object -First 1
```

工具自带的诊断入口：

```bat
dist\_selftest.exe biquga                 :: PC 版：搜索 + 目录遍历
dist\_selftest.exe dl /69_69707 6         :: 移动版：小样本真下载（会打印表头）
dist\_selftest.exe fanqie 7256784068786785336
dist\_diag.exe                            :: 移动版目录页诊断
```
