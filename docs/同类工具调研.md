## 3. 最值得借鉴的 5 个功能

排序依据：**实现成本（越低越好）× 用户价值（越高越好）× 法律/风控风险（越低越好）**。

### 🥇 第 1 名：配置化书源规则 + 站点级限速覆盖

**为什么排第一**：这是唯一一个「一次投入、长期免维护」的功能。所有高 Star 项目最终都收敛到它——`so-novel` 用 [rule-template.json5](https://github.com/freeok/so-novel/blob/main/bundle/rules/rule-template.json5) 把整站适配压缩成一个 JSON5 文件（CSS/XPath 选择器 + `@js:` 脚本钩子），站点改版时用户自己就能改规则，作者不必跟版。

更关键的是它把**限速做成了规则的一部分**——`crawl` 块支持按书源单独设置 `concurrency / minInterval / maxInterval / maxAttempts`：

```json5
"crawl": {
  "concurrency": 1,        // 该站只允许 1 并发
  "minInterval": 1000,     // 请求间隔 1~3 秒
  "maxInterval": 3000
}
```

`so-novel` 据此分出 [rate-limit.json](https://github.com/freeok/so-novel/blob/main/bundle/rules/rate-limit.json)、[proxy-required.json](https://github.com/freeok/so-novel/blob/main/bundle/rules/proxy-required.json)、[cloudflare.json](https://github.com/freeok/so-novel/blob/main/bundle/rules/cloudflare.json) 四套书源集。**实现成本低**（就是数据结构设计），**用户价值高**（新站点当天可用），**风险低**（限速是降低风险的方向，不是抬高）。

### 🥈 第 2 名：断点续传 + 缺章补齐（真正颗粒度到「章」）

**为什么排第二**：这是 issue 区里呼声最集中、但现有项目普遍做得最糙的功能。`so-novel` 用户明确提「支持增量下载以补全多次重试仍失败的章节，避免重复下载全本」（见 [so-novel issues 列表](https://github.com/freeok/so-novel/issues?q=is%3Aissue)）；`ying-ck` 有 25 条评论的「[下载到一半失败](https://github.com/ying-ck/fanqienovel-downloader/issues/159)」问题。`FictionDown` 的做法最值得抄——它落盘一个中间态文件，**强制结束再跑就从上次断点继续**，且能「只爬 VIP 部分」做局部补齐。

**成本中等**（要设计章节级状态存储），**用户价值极高**（百万字小说下载两小时，断一次全废是不可接受的），**风险为零**（纯本地行为）。

### 🥉 第 3 名：导出格式分层（TXT 保底 + EPUB 主推）

**为什么排第三**：TXT 是 13/15 的保底能力，EPUB 是 12/15 的主推，但**真正拉开差距的是「生成后能被主流阅读器打开」**。`FictionDown` 在 README 里诚实承认「支持导出 epub（还有些问题，某些阅读器无法打开）」，并给出 `pandoc --epub-chapter-level=2` 的绕行方案；`so-novel` 需要专门开讨论帖修 [WPS、掌阅无法打开 EPUB 的问题](https://github.com/freeok/so-novel/discussions/199)。

**建议做法**：EPUB 走「标准合规优先」而非「功能优先」，提供 Markdown 作为逃生出口（`FictionDown` 就是这么干的，md 可再交 pandoc 转任意格式）。**成本低**（库都现成），**价值高**，**风险低**。

### 第 4 名：请求节流与指数退避（把「礼貌」做成默认值）

**为什么排第四**：`so-novel` 的默认配置值得直接抄——最小间隔 200ms、最大 400ms、重试间隔 2000~4000ms、最大重试 3 次；对 `0xs.net` 这种「线程数为 1 也会被限流」的站点，规则里直接写 `concurrency: 1` 并在 `comment` 里说明后果。`FictionDown` 也提醒「起点和盗版站的页面可能随时更改」。

用户价值在于**稳定性**（请求被拒绝时是退避重试而不是崩掉），风险侧是**唯一能主动降低风控概率的工程手段**。成本极低。

### 第 5 名：正文清洗（去广告/水印/页码）

**为什么排第五**：`so-novel` 的规则里 `filterTxt` 是正则数组式的清洗模式，`filterTag` 丢弃标签，`paragraphTagClosed` / `paragraphTag` 处理段落分隔——这三件套能解决 90% 的正文脏数据。看看实际要清理什么就知道价值：`"首发网址.+。|\(本章完\)|一秒记住【新天禧小说\s*】手机用户输入地址：..."`、`"最⊥新⊥小⊥说⊥在⊥六⊥9⊥⊥书⊥⊥吧⊥⊥首⊥发！"`（用分隔符绕过关键词匹配的水印）。**成本低**（正则配置），**价值中等偏高**（直接决定成品可读性），**风险低**。

### ⛔ 明确不建议做的功能

| 不建议做 | 理由 |
|---|---|
| **绕过验证码 / 人机校验** | 番茄系项目的 issue 区反复出现「[疑似出现客户端ID保护](https://github.com/ying-ck/fanqienovel-downloader/issues?q=is%3Aissue)」「[现有的cookie策略不奏效，陷入长循环](https://github.com/ying-ck/fanqienovel-downloader/issues?q=is%3Aissue)」。这类对抗是**军备竞赛**：赢了要持续投入，输了项目就死。而且「绕过访问控制措施」在法律定性上明显比单纯抓公开页面更不利。 |
| **破解付费 / VIP 章节、突破章节数上限** | `ying-ck` issue 区有「[已付费还是只能下载400章节](https://github.com/ying-ck/fanqienovel-downloader/issues?q=is%3Aissue)」——这类需求一旦满足，性质就从「格式转换」变成「规避付费墙」。对比看 [404-novel](https://github.com/404-novel-project/novel-downloader) 的合规做法：README 明写「**如欲下载付费章节，请登录相应网站帐户，并确定已购买相应付费章节。未登录或未购买的章节，下载时将直接忽略**」——**这才是可以借鉴的边界设计**：只下载用户已有权访问的内容，脚本本身不提供任何越权能力。 |
| **内置 / 分发书源规则集合** | `any-reader` 的做法是标杆：README 顶部反复强调「**软件不提供内容，也不提供任何规则**」，并警告「运行不受信任规则时有安全性风险！因为规则可以利用 JS 越权」。自己内置一堆盗版站规则，等于把侵权责任从用户转移到你身上。**让规则由用户自备、可导入，是免责设计而非功能缺失。** |
| **内置 Cloudflare 绕过 / 反爬对抗模块** | `so-novel` 是通过 `cf-bypass` 配置项**对接第三方服务**（[CloudflareBypassForScraping](https://github.com/sarperavci/CloudflareBypassForScraping)），而不是自己实现绕过。这个边界划得很聪明：能力外置、责任外置，自己只做「配置项」。 |
| **批量无节制下载 / 开放公网 Web 服务** | [Tomato-Novel-Downloader](https://github.com/zhongbai2333/Tomato-Novel-Downloader) 专门做了两件反向操作：**CLI 已禁用 `--download` 新建下载能力**（"以降低脚本批量滥用风险"）、`--update` 只允许更新本地已有记录的书；Web UI「**如果要暴露到公网，建议放在反向代理/HTTPS 后面，并务必开启密码锁**」。**主动限流和限制滥用面，是这个领域里项目能活得久的关键。** |

### 4.2 字体加密 / 反爬字符

番茄小说的反爬方式是**用自定义字体把正文常用字替换成私有字形**，分两条技术路线：

- **OCR 路线**：[FanqieFetch](https://github.com/hxhy00/FanqieFetch) 下载 woff2 → 每个字形渲染成图片 → OCR 得到 `{Unicode: 真实文字}` 字典 → 替换回正文。代价是**需要人工确认字库的 GUI**（`--manual` 参数），且识别不准就会缺字。
- **映射破解路线**：[romcere/fanqienovel-decryptor](https://github.com/romcere/fanqienovel-decryptor) 直接维护 `font_map.py` 映射字典。

**关键警告（来自项目自身 README）**：`fanqienovel-decryptor` 明确写道「该项目已完成字体解密工作，但**由于番茄小说网站的限制（验证码、无法阅读全文）等原因，无法下载全部章节**，拥有番茄SVIP除外。**这也是为什么大多数相关工具需要API的原因**」。

→ **这是整个番茄生态的技术真相**：字体解密 ≠ 能拿到全文，真正的门槛是验证码和阅读权限。所以**不要投入大量精力做字体反混淆**，投入产出比极低，且直接踩反爬红线。

### 4.5 编码问题

- **输出编码**：`so-novel` 提供 `txt-encoding` 配置（默认 UTF-8，可设 GBK「以兼容旧设备」）；`shing-yu` 让用户在 UTF-8 与 GB2312 间选择；`rainyautumn1` 在更新日志里写「**强制 UTF-8 编码**」作为反爬虫增强的一部分。

- **依赖编译编码**：`ying-ck` README 专门写了一段「安装 lxml 库可能报错」的解法：`CFLAGS="-O0" pip install lxml`。

**建议**：输入编码自动探测（`chardet`/`charset-normalizer`）、输出编码可配、运行环境编码显式设置——三处都要管。

## 5. 总结：如果只允许加 2 个功能

**建议加：（1）配置化书源规则引擎（含站点级限速覆盖）；（2）章节级断点续传与缺章补齐。**

理由是这两件事分别解决了这个领域**「项目会死」的两个真正原因**，而不是在功能清单上多打一个勾。

第一个原因是对抗性维护成本：`so-novel`（8,292★）和 `any-reader`（1,190★）能成为同赛道第一梯队，靠的不是爬虫代码写得多好，而是把「站点改版」这件事从**作者的维护负担**转成了**用户可自助的配置**——一个 JSON5 文件改几行选择器就能修好一个站，作者不必跟版，项目因此活得久。而 `shing-yu/fanqie-novel-download`（420★）的停更公告「所依赖的API已经不再可用（包括上游项目）」正是反例：**硬编码站点的项目，站点一变就整体死亡**。把并发数和请求间隔做成书源级参数，则是在同一个数据结构里顺手解决了风控问题——按 [rate-limit.json](https://github.com/freeok/so-novel/blob/main/bundle/rules/rate-limit.json) 的实测记录，有的站并发 5 还行，有的站并发 1 都会被限流并把正文替换成辱骂式警告，**没有站点级配置，你要么全局慢到不可用，要么全局快到被封**。

第二个原因是用户实际流失点：小说动辄百万字、上千章、下载耗时以小时计，而现有项目的断点续传普遍做得不够细——`so-novel` 的 issue 区至今挂着「支持增量下载以补全多次重试仍失败的章节，避免重复下载全本」的功能请求，`ying-ck` 有 25 条讨论的「下载到一半失败」问题。`FictionDown` 的做法（落盘中间态、强制结束再跑从断点续、能只爬缺失的 VIP 部分）是这批项目里最扎实的参考实现。**这两个功能都不碰法律红线**（规则引擎是数据结构，断点续传是纯本地状态），**成本可控**（一个是 schema 设计，一个是状态存储），却能同时降低你的长期维护成本和提高用户的留存率——相比之下，做字体反混淆（投入产出比已被 `fanqienovel-decryptor` 的 README 亲口否定）或做付费章节解锁（直接把项目定性为规避付费墙）都是性价比极低甚至自毁的选择。
