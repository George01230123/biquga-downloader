# 更新已下载的书 / 导出 EPUB

这两个功能是看了同类开源工具之后加的（调研笔记见 `docs/同类工具调研.md`）。
它们对应两个共性缺口：**"网站更新了，难道要重下一遍？"** 和 **"txt 在手机上不好读"**。

---

## 一、更新已下载的书（增量更新）

### 怎么用

1. 先正常下载一本（「下载全部章节」）
2. 过一阵子想追更新时：重新「载入目录」（或「刷新目录」拿最新目录）
3. 点 **「更新新章节」**

程序会告诉你"发现 N 章新章节"，然后**只下这 N 章**，追加到已有 txt 的末尾。

### 它是怎么知道"哪些是新的"

靠写进 txt 表头的一行进度标记（每次下载/更新都会更新它）：

```
本次下载：成功 1027 章，跳过 40 章，失败 0 章  #progress-ok:1027:ef9c6eacd646
```

- `1027` = 已经写进正文的章节数
- `ef9c6eacd646` = **前 1027 章 id 的指纹**（MD5 前 12 位）

更新时程序做两件事：

1. 用当前目录的前 1027 章重算指纹 → **和文件里存的比对**。不一致说明站点改了目录顺序或换了源，
   这时**拒绝追加**（追加会让正文顺序错乱），提示你刷新目录后重下整本。
2. 指纹一致 → 第 1028 章起就是新的，只下这些。

> **旧文件（v1.0.3 之前下载的）没有这行标记**，程序会明确提示"没法安全判断"，让你重下一遍。
> 这不是偷懒：没有标记就只能猜，猜错会把正文写乱。

### 为什么不会弄坏老正文

txt 的表头区是**定长 2KB**：正文从固定偏移开始，更新时重建表头块（表头 + 补白 + `#header-zone` 标记行）
写回去，**字节数严格守恒**，所以标记行和正文起点一动不动，新章节只是 append 在后面。

这条不变量有 16 条离线断言守着（`tests/OfflineTests.cs` 的 `TestIncrementalAppend`）：
表头区字节数不变、旧正文前缀一字未动、文件只变长、章节顺序递增、进度标记正确更新。

开发这段时踩过的坑（都记在代码注释里）：

| 坑 | 症状 |
| --- | --- |
| 把 ASCII 解码后的**字符下标**当**字节偏移**用 | 覆盖长度算大 2 倍多，把"下载时间/等号行"整段覆盖掉 |
| "往后找行首"定边界 | 命中了补白里的换行，后面几行被当补白填掉，**46 个等号那行直接消失** |
| 定长补齐 vs "放不下就放弃" | 两者互相打架，统计永远更新不了 |
| `#header-zone` 标记没自成一行 | 往前找行首会落到补白里，同样吃掉后面的行 |

最终做法（简单且不会错）：**整个表头块重建**，只有一个约束 —— 新块字节数必须等于旧块，
否则整体放弃（宁可统计不更新，也绝不越界）。

## 二、导出 EPUB

### 怎么用

点 **「导出 EPUB」**。它会：

1. 优先用内存里已下载的正文；没有就按章节标题从已生成的 txt 里**反解析**回来
2. 在书目录里生成 `书名.epub`（手机阅读器、Kindle 都能直接打开）

**不联网**，纯本地转换。

### 实现说明

零依赖手写 zip（`src/Common/EpubWriter.cs`）：EPUB 本身只是个有约定的 zip，
.NET 自带 `ZipArchive` 就够，不需要引第三方 EPUB 库 —— 这个项目的卖点就是"单文件、零依赖"。

规范上必须注意的两点（踩了有的阅读器直接打不开）：

1. **`mimetype` 必须是第一个条目，且不能被压缩**。
   实测 .NET 的 `CompressionLevel.NoCompression` 是"deflate 头 + stored 块"，
   字节确实没被压缩（20 字节原文存成 25 字节，多出来的是块头开销），但压缩方式字段是 8 不是 0 ——
   所以断言不能写"字段==0"，要检验"没有真压缩"。
2. **所有 XML/XHTML 必须转义正确**：正文里的 `<`、`&` 不转义会让 XHTML 解析失败、整本书打不开。
   离线断言里用 `XmlDocument.LoadXml` 真解析了每个 XHTML/OPF/container.xml。

结构：

```
mimetype (不压缩，第一个)
META-INF/container.xml
OEBPS/content.opf          ← 清单 + 阅读顺序 + 元数据（书名/作者/语言/简介）
OEBPS/nav.xhtml            ← 目录（EPUB3 的导航文档）
OEBPS/style.css
OEBPS/text/chapter0001.xhtml …  ← 每章一个文件（编号补零，保证阅读器里顺序正确）
OEBPS/images/cover.jpg + text/cover.xhtml   ← 有封面才写
```

### 实测数据

| 书 | 章节 | 源 txt | 生成的 EPUB |
| --- | --- | --- | --- |
| 牧神记（牧神纪） | 1026 章 | 10.4 MB | 5.34 MB |

> 注意：FictionDown 的 README 提到"生成的 EPUB 可能过大，部分阅读器会卡顿"。
> 上千章的书建议用支持分章的阅读器（多看、静读天下、Apple Books 都正常）。

## 三、还没做的

对比同类工具后**明确不做**的（理由见 `docs/同类工具调研.md`）：

- **配置化书源规则引擎**：同类工具（so-novel 8.3k star）靠这个活得很好，但它的前提是
  "软件不提供内容，也不提供任何规则"——规则由用户自己写。这个方向工程量大，
  而且稍不注意就会变成"内置分发书源"，**本次不做**。
- **绕验证码 / 破解付费章节**：直接越过合规红线，不做。
- **字体反混淆**：`fanqienovel-decryptor` 的作者自己说"解密了字体也拿不到全文（还有验证码和阅读权限）"，
  ROI 极低，不做。
- **PDF / MOBI / AZW3**：MOBI/AZW3 需要外部工具，PDF 排版效果差；有 EPUB 就够了。
